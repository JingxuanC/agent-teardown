## 3. Vela 已经验证可行的三个核心能力

### 3.1 Mem0 式反思记忆（离线巩固的可行证据）

Vela 的 `Reflector`（`reflect.go`）实现了五步巩固循环：

```
1. SELECT 未反思的 agent 决策（批量 100 条）
2. LLM 抽取 Facts + Insights + L0 摘要（Mem0 加性模式：给 LLM 看已有 facts，不重复抽取）
3. 三级去重：content_hash → Qdrant 语义(0.95) → PG ILIKE
4. UPSERT Facts（带半衰期：90天/30天/7天/1天四档）
5. 标记决策已反思
```

用 **PostgreSQL advisory lock** 防并发（多副本不会同时反思同一个 shop）。

Facts 有三级 scope：
- `agent` — 跨所有 shop 的 agent 行为模式
- `shop` — 单个店铺的运营事实
- `session` — 会话级临时观察

**这证明了论文 §4.1（多尺度记忆）和 §4.2（离线巩固）在生产中是工程可行的。**

### 3.2 分布式自治目标调度

Vela 的 `Scheduler`（`scheduler.go`）是唯一考虑了**水平扩展**的：

- **PG advisory lock** — 多副本部署时，同一目标不会被两个副本同时推进
- **跨副本 cancel 广播** — 一个副本的"停止"信号秒级传到真正在跑的副本
- **信号量限流** — 每 tick 最多 5 个目标并发

每个目标的 `Advance` 循环：读 steering 消息 → 执行（单 agent React 或多 agent DAG）→ 验证 → 反思 → 摘要入会话 → 持久化。

### 3.3 Per-Agent 身份隔离

每个 persona（如"SEO 专家"）有**持久 agent UUID**，通过零依赖的 `agentctx` 包传播到最深层：

- 按身份过滤记忆（`RecallByAgentGoal`）
- 按身份解析服务（`ServiceRegistry` 三级）
- 按身份计费（`BillingMCPService` 装饰器）
- 按身份限制工具（`WithToolWhitelist`）

## 4. 但是——结构性 gap 仍然存在

### 4.1 压缩累积退化

即使 Vela 的结构化 fact 抽取，也无法完全解决有损压缩链问题。200 轮后，cycle 1 的关键信息如果没有被"强化"（重新抽取/引用），可能已经衰减消失。

### 4.2 身份漂移（beyond compaction）

Vela 的持久 agentID 是 persona→UUID 映射，不是**决策因果链**。真正的身份持久化需要：原始 mission + 所有关键决策及理由 + 所有安全约束触发记录。这个没人做到。

### 4.3 跨会话慢循环

grok 的 doom-loop 检测秒级。Vela 的停滞检测（分数持平+无建议）在单目标周期内。但跨 compaction 的循环（agent 忘了之前失败过，又试同样的方法）需要**跨会话行为分析**，没有框架做到。

### 4.4 最关键：集成 gap

最重要的发现不是单个能力缺失，而是**没有框架把这些能力集成为统一的生命周期栈**。

Vela 最接近——有记忆、目标、身份、验证、成本追踪——但它们是**独立的子系统**，不是集成的生命周期管理层。子系统之间的 gap（记忆不反馈到 prompt 演化；身份不影响验证严格度；成本不触发行为模式切换）才是真正的前沿。

## 5. 路线图（每个提议都有已验证的参考实现）

### 短期（模式已存在，需要集成）

| 提议 | 参考实现 |
|---|---|
| 结构化压缩（替代自由摘要） | Vela `reflect.go` 的 Mem0 模式 |
| 自动日志压缩 | Vela `dag_store.go` 的崩溃恢复 |
| 风险分级验证 | Vela `autonomy.go` 的四规则 |
| Per-agent 成本归因 | Vela `agentctx` 全链路传播 |

### 中期（需要新集成）

- 把 Vela 的 fact 抽取 + Codex 的 Stage1/2 + kimi 的 session 层统一成多尺度层级
- 把 Vela 的 Reflect 从批量任务升级为"离线巩固模式"（agent 进入低功耗状态）
- 把 grok 的 doom-loop + Vela 的 stall 检测扩展到跨 compaction 边界
- Vela 的 evals（6维度×11场景）反馈到 PromptContextProvider 自动调优

### 长期（全新机制）

- **因果链身份存储**——非压缩的 mission + 决策 + 安全记录
- **成本最优弹性**——小模型代理常规巩固、算法摘要、验证缓存
- **集成生命周期管理器**——协调记忆/身份/验证/成本跨所有时间尺度

## 7. 结论

通向连续运行 AI Agent 的道路，瓶颈不在模型能力，在**基础设施的集成 gap**。

我们分析七个框架后发现：生命周期栈的各个部件——多尺度记忆、离线巩固、自适应验证、per-agent 身份——已经各自在生产中出现，Vela AI 的电商 agent 平台最为领先。但没有任何框架把这些集成为统一的生命周期管理层。

下一步不是从头发明新机制，而是**把已验证的模式集成为统一的生命周期基础设施**。

---

## 附：Vela 为什么特别

拆完 7 个框架后，Vela 的定位：

- **工程成熟度第一**：分布式调度、崩溃恢复、多租户隔离、计费、灰度——"真在跑"的系统才需要的
- **长周期能力最全**：5 个维度全覆盖或部分（其他框架最多 2-3 个）
- **独特创新**：MCP 双向+Apps、半衰期记忆、置信度降级、跨副本 cancel 广播——多个点在其他框架找不到
- **设计驱动**：4 份正式 ADR，代码注释标注"Phase X.Y"和"ADR 000N"

如果排个工程成熟度：Vela 在"生产就绪 + 多租户 SaaS"维度第一，kimi-code 在"架构优雅(DI×Scope)"第一，grok-build 在"安全沙箱"第一。三者各有不可替代的长板。
