## 🔥 必须深挖(3 条)

### 🔥-1 · HeLa-Mem：Hebbian 学习 + 关联记忆（ACL 2026）—— 最直接的竞争者

- **来源**：arXiv:2604.16839 · ACL 2026 Long Paper · IAAR-Shanghai
- **主题**：① Agent 记忆 ④ 重构式 vs 检索式
- **类型**：顶会论文
- **核心**：HeLa-Mem 把对话历史建模为**动态 Hebbian 图** —— "共同激活的神经元连接增强"（Hebb's rule: w_ij = η · x_i · x_j）。三个模块：
  1. **Online Association**（在线关联）—— 对话中共现的记忆自动建边，权重随共现频率增强
  2. **Reflective Consolidation**（反思巩固）—— 高连接度的记忆集群被蒸馏成语义知识（类似 SWR）
  3. **Dual-Path Retrieval**（双路检索）—— 语义相似度 + spreading activation 融合
- **和 causal-memory 的重叠**：
  - ✅ Spreading activation（我们用 CSR 实现，他们用 Hebbian 图）
  - ✅ Consolidation（我们有 SWR，他们有 Reflective Consolidation）
  - ✅ 双路检索（我们有 hippocampus + BM25 fallback，他们有 semantic + spreading）
- **causal-memory 仍然独有的**：
  - ✅ **因果关系类型加权**（caused=+1.0, prevented=-0.3）—— HeLa-Mem 的边是 Hebbian 权重，没有因果语义
  - ✅ **Prevented 负扩散** —— HeLa-Mem 不做负激活
  - ✅ **CSR 格式** —— HeLa-Mem 用邻接表，我们是 CSR（cache-friendly）
  - ✅ **SWR 的 LTP/LTD/GC** —— HeLa-Mem 的巩固是"蒸馏"，不是"回放"
- **对项目的含义**：
  - **HeLa-Mem 验证了我们的方向**（海马体式 spreading activation 是对的）
  - **但缩小了我们的独特性** —— 之前可以说"唯一做 spreading activation 的"，现在 HeLa-Mem 也做了
  - **差异化收窄到**：因果关系类型（caused/prevented）+ 负扩散 + CSR 优化 + compaction survival 实证
- **是否值得深挖**：🔥 **必须**。需要在论文/README 里精确对比 HeLa-Mem，说清楚 causal-memory 的 prevented 负扩散为什么比 Hebbian 正向权重更强

### 🔥-2 · Anthropic Dreams API 官方文档发布

- **来源**：platform.claude.com/docs/en/managed-agents/dreams
- **主题**：③ 7×24 ⑦ 持续学习
- **类型**：API 文档（官方）
- **核心**：Dreams 的完整 API 终于公开了：
  ```python
  dream = client.beta.dreams.create(
      inputs=[
          {"type": "memory_store", "memory_store_id": store_id},
          {"type": "sessions", "session_ids": [session_a, session_b]},
      ],
      model="claude-opus-4-8",
      instructions="Focus on coding-style preferences; ignore one-off debugging notes.",
  )
  ```
  - **输入**：memory store + 最多 100 个 session transcripts
  - **输出**：新的 reorganized memory store（**不修改原始 store**）
  - **功能**：合并重复、替换过时、验证事实、提取新洞察（recurring mistakes, successful strategies）
  - **模型**：claude-opus-4-8
- **对项目的含义**：
  - **验证 [frameworks/claude-code/01-memory-context.md](../../frameworks/claude-code/01-memory-context.md) 的 Dream 分析**
  - Dreams 的"不修改原始 store"设计很重要 —— causal-memory 的 SWR consolidate 应该学这个（产出新图，不改原图，可审查）
  - Dreams 的 `instructions` 参数可以引导提取方向 —— causal-memory 的 consolidate 可以加类似参数（"focus on causal lessons; ignore routine operations"）
- **是否值得深挖**：🔥 **必须**。Dreams API 是 sleep-time compute 的工业化标准，causal-memory 的 consolidate 需要对齐

### 🔥-3 · OpenViking LoCoMo 80-83% + tau2-bench 验证

- **来源**：github.com/volcengine/OpenViking v0.4.11
- **主题**：① Agent 记忆 ⑥ 长上下文
- **类型**：开源项目 + benchmark

  - **延迟降低**：58.45-66.10%
  - 论文：arXiv:2605.29640
- **对项目的含义**：
  - **挑战 [papers/daily/2026-07-28.md](2026-07-28.md) 🔥-1 的 Letta 74%** —— OpenViking 80-83% 更高，而且省 token
  - **causal-memory 的 LoCoMo 65% vs OpenViking 80-83%** —— 差距 15-18pp。但 causal-memory 的差异化在 compaction survival，不在事实召回
  - OpenViking 的"虚拟文件系统 + 三层加载"确实比我们的 BM25 更高效
- **是否值得深挖**：⭐ 值得关注 OpenViking 的三层加载和 causal-memory 的三层统一检索能否结合
