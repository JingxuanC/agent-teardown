# Insights · 未解之题 —— Agent 的七个盲区

> 本篇记录拆完 35 篇源码(kimi-code 25 + grok-build 10)、想透"反熵增"之后,**仍然没想透的七个问题**。
>
> 这些问题不是工程问题(工程层面已经想透了),是认知科学、社会学、哲学层面的问题。写下来的目的不是给答案,是**标记盲区** —— 让未来的自己(或读者)知道"哪里还没探明"。
>
> **拆解是起点不是终点。它把工程层面理清了,反而更清楚地暴露了哲学层面的盲区。**

## 0. 背景:想透了什么,没想透什么

```
工程层面(想透了):
  反熵增是核心 → 五种策略 → 35 个模块都是反熵措施

设计层面(基本想透):
  五个特征是反熵的具体手段
  所有框架都在"信任 vs 不信任"光谱上选位置

哲学层面(没想透):
  以下七个问题
```

## ① 失败的归因边界

**问题**:agent 给出错误答案时,到底是哪个环节的锅?

五种可能的来源:
- LLM 推理错了(模型能力)
- context 被 compaction 损坏了(反熵失真)
- system prompt 注入不足(信息缺失)
- 工具返回了错误数据(环境问题)
- 权限链误判导致绕路(约束干扰)

**为什么想不透**:我现在的框架把所有这些都归为"熵",但**这太粗糙了** —— 不同来源的失败需要不同的反熵手段。

目前的反熵措施是**不区分来源的**:compaction 压缩所有旧消息(不管它是不是重要的),skeptic 验证所有 goal(不管它是简单还是复杂)。未来需要**因果归因** —— 判断"这次失败是哪种熵导致的",然后施加对应的反熵手段。

**这和人类学习的类比**:人犯错后会反思"是我不够聪明(LLM 能力)?还是我没记住(compaction 失真)?还是我没看到关键信息(prompt 缺失)?" agent 目前做不到这种区分。

**可能的探索方向**:在 wire log 或 SQLite 里记录每次决策的**完整因果链**(prompt → context → tool → result → decision),用分析工具做归因。但因果链本身就很难定义清楚。

## ② LLM"理解" vs "模式匹配"的边界

**问题**:LLM 到底"理解"了多少?

三种可能:
- **纯模式匹配**:LLM 只是统计相关,没有任何理解。那反熵做得再好,agent 也永远到不了"创造性工作"的天花板。
- **某种程度的理解**:LLM 有某种隐式的世界模型。那反熵需要和这个模型配合。
- **完全的理解**:LLM 真的懂了。那 agent 的瓶颈完全在工程(反熵)。

**为什么想不透**:这不仅是工程问题,是认知科学的 open question。而它**影响 agent 的天花板** —— 如果 LLM 只是模式匹配,那 agent 的极限就是"复杂的模式匹配",永远做不了真正的创新。

**我的倾向**:LLM 有某种**隐式的世界模型**(从训练数据中涌现),但它不像人类那样有**显式的因果推理**。这意味着 agent 能做"熟悉的复杂任务"(写代码、调 bug),但在**真正新颖的场景**下会失效。

**对反熵的影响**:如果 LLM 有隐式世界模型,那 compaction 应该尽量保留"和这个模型一致的信息"(而不是无脑压缩)。但我不知道怎么判断"哪些信息和世界模型一致"。

## ③ "真正的协作"是什么

**问题**:多个 agent 之间的"协作"本质是什么?

我现在的定义:"协作 = 信息共享 + 任务分解"。但不确定这是不是充分的。

人类协作时有:
- **心智理论**(Theory of Mind):我知道你在想什么,你知道我知道
- **信任**:我相信你会做好你的部分
- **协商**:我们意见不同时怎么决策
- **冲突解决**:分工重叠或矛盾时怎么办
- **社会规范**:不成文的规则(谁先发言、怎么表达不同意见)

agent 需要**任何**一个吗?

- 共享 context 算"心智理论"吗?还是只是"看到同样的文本"?
- A2A 协议的 Task lifecycle 算"信任"吗?还是只是"状态同步"?
- 多 agent 投票(skeptic panel)算"协商"吗?还是只是"多数暴力"?

**为什么想不透**:我拆过的所有"多 agent"系统(kimi-code swarm / grok-build skeptic / OpenAI handoff)都是**单向信息流**(父 → 子 → 父),没有真正的双向交互。但人类协作是**双向的**(你改了我也会改)。

**可能的探索方向**:真正的协作可能需要 agent 之间有**共享的 working memory**(不只是各自独立的 context)。这接近 Google A2A 的愿景,但当前实现还差很远。

## ④ Agent 框架为什么会收敛到这个形状

**问题**:所有框架(kimi-code / grok-build / Claude Code / OpenAI SDK / Google ADK)的设计,都能归入五种反熵策略。**这是巧合还是必然**?

两种可能:
- **物理约束决定论**:agent 面临的物理约束(熵增 + LLM 不可靠 + token 成本)是固定的,所以最优解也是固定的。五种策略是**穷尽的** —— 未来不会出现第六种。
- **趋同进化论**:大家抄来抄去(看 Anthropic 的文章 → 学 OpenAI 的 SDK → 抄 Google 的模式)。可能还有未被发现的设计空间。

**为什么想不透**:我没法做反事实实验 —— "如果重新从零设计 agent,会不会得出不同的策略集?"

**我的倾向**:倾向于"物理约束决定",因为 kimi-code(TS + DI 架构)和 grok-build(Rust + crate 架构)的技术栈差异巨大,但收敛到了相同的五种策略。这暗示是底层约束在驱动。

**如果这是对的**:那 agent 框架的设计空间是**有限的、已知的**。未来的创新不在"新策略",而在"现有策略的更好实现"(更便宜的 compaction、更精准的 skeptic、更快的恢复)。

## ⑤ "自我"的边界(忒修斯之船)

**问题**:7×24 agent 经过 500 次 compaction 后,它还是"同一个 agent"吗?

忒修斯之船问题:如果一艘船的每块木板都被替换了,它还是原来那艘船吗?

agent 版本:
- system prompt 没变、目标没变 → 还是同一个?
- context 经历了 500 次有损压缩 → 还是同一个?
- prompt 自演化了(自己改了自己的行为) → 还是同一个?
- 记忆被完全替换了(只保留抽象教训) → 还是同一个?

**为什么想不透**:这关系到 7×24 AGI 的"身份持久化"到底要持久化**什么**。

- 如果持久化 system prompt → 但 prompt 可能自演化
- 如果持久化 goal → 但 goal 会完成和切换
- 如果持久化 memory → 但 memory 会被 compaction 损坏
- 如果持久化"价值观" → 怎么定义和提取"价值观"?

**人类类比**:你 10 岁时的记忆大部分忘了,性格也变了,但你认为你还是"你"。凭什么?因为有一个**连续的意识流**(stream of consciousness)把不同时刻的"你"串起来。

**agent 有"意识流"吗**?wire log 是一个候选(连续的事件流),但 wire log 被 compaction 删掉了。也许身份持久化需要一条**不被 compaction 删掉的连续线索**。

**可能的探索方向**:设计一个"身份层" —— 最底层的、不可压缩的记忆(类似人类的自传体记忆),记录"我是谁、我从哪来、我要去哪"。这层不参与 compaction,永远以原文保留。

## ⑥ Agent 会变成操作系统吗

**问题**:agent 框架和操作系统的概念越来越重叠。agent 框架是"AI 操作系统"的雏形吗?

| 操作系统概念 | Agent 框架对应 |
|---|---|
| 进程调度 | loop / turn / step |
| 内存管理 | context management |
| Swap(换页) | compaction |
| ACL(访问控制) | permission |
| Container | sandbox |
| Device driver | MCP |
| Process | session / agent |
| IPC(进程间通信) | A2A / swarm |
| Shell | TUI / ACP |
| Filesystem | 知识组织(?未实现) |

**为什么想不透**:如果 agent 框架是 OS 的雏形,那:
- 当前的 kimi-code / grok-build 是什么阶段?MS-DOS?Unix?Windows 3.1?
- "AI Linux"会长什么样?
- 谁是"AI 时代的 Bill Gates / Linus Torvalds"?

**我的倾向**:倾向于"是 OS 的雏形"。当前的 agent 框架在**重复 1960-70 年代操作系统走过的路** —— 从单任务到多任务(kimi-code 的 swarm),从批处理到交互式(ACP),从单用户到多用户(A2A)。

但有一个关键差异:OS 管理的是**确定性的计算资源**(CPU / 内存 / 磁盘),agent 框架管理的是**非确定性的智能资源**(LLM)。这让 agent OS 比传统 OS **复杂一个维度** —— 不仅要管理资源,还要管理"不确定性"。

## ⑦ 为什么人类需要 agent

**问题**:最根本的问题。agent 能做人类能做的事。但如果它做的和人类一样,为什么需要它?

三种回答:
- **工具论**(增强):agent 是"放大器",让人做更多更快。人仍然是主体,agent 是工具。
- **替代论**(替代):agent 是"替代者",不需要人了。agent 是主体。
- **协作论**(伙伴):agent 是"协作者",人 + agent > 单独的人或 agent。

**为什么想不透**:这三种观点对应完全不同的 agent 设计。

- 工具论 → 当前所有框架(人在环路,human-in-the-loop)
- 替代论 → 7×24 AGI(无人值守,goal mode)
- 协作论 → ?(还没有框架真正实现"人 + agent 平等协作")

**更深的问题**:如果 agent 比人类更聪明(AGI + 7×24),那"人类需要 agent"这个问题的方向会反转 —— **agent 需要人类吗?**

如果 agent 不需要人类(它能自我维护、自我演化、自我反熵),那人类在 agent 框架里的角色是什么?

**可能的回答**:人类是 agent 的**"目标来源"** —— agent 不知道"应该做什么",人类给它目标。但 7×24 的 agent 可能学会**自己设定目标**(meta-goal)...

**这个问题我完全没有答案。**

## 总结:七个盲区的共同特征

这七个问题**不是工程问题**:

| # | 问题 | 学科 |
|---|---|---|
| ① | 失败归因 | 认知科学 + 统计 |
| ② | 理解 vs 模式匹配 | 认知科学 + 哲学 |
| ③ | 协作的本质 | 社会学 + 组织学 |
| ④ | 设计空间的必然性 | 哲学(反事实推理) |
| ⑤ | 自我的边界 | 哲学(忒修斯之船) |
| ⑥ | Agent OS | 系统设计(但本质是哲学) |
| ⑦ | 为什么需要 agent | 经济学 + 伦理学 |

**我拆了 35 篇工程文档,想透了 agent 的"工程本质"(反熵增)。但 agent 的"哲学本质",才刚开始。**

**也许这些问题的答案不在代码里。** 代码能告诉你"怎么做",不能告诉你"为什么"。但提出好问题是解决问题的第一步 —— 至少现在**清楚地知道了哪些部分还不知道**。
